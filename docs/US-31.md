# US-31: Automatically recalculate cumulative GPA

Issue: [#39](https://github.com/forq-forq-forq/academic-advisor/issues/39).

## Existing implementation and dependency

Before US-31, GPA was a stored `Student.gpa` value, seeded as 3.8 or initialized
as 0.0 on registration. `AcademicStandingDto` formatted that value; no GPA
calculation service existed. The FAQ supplied the weighted formula and the
examples C=2.0 and D=1.0, but not the complete scale.

This branch starts at US-29 PR #38's reviewed head `06df5ca`. Its PR targets
`feat/US29-completed-course-history` while #38 is unmerged. Consequently its diff
contains only US-31 changes, without copied entities or migrations. After #38
merges, rebase the US-31-only commits onto main and retarget the PR to main before
merging it. If #38 is squash-merged, use the old dependency head as the rebase
boundary so its commits are not replayed. No automatic merge is intended.
CI also accepts PRs targeting this specific dependency branch, since the original
workflow ran only for PRs into main; this makes the stacked PR's checks executable.

Dependencies/conflicts: US-29 supplies the grade records; a future transcript
editor/importer supplies changes (US-30), but no editor is needed for read-time
recalculation. US-07's badge must use calculated GPA. US-42's chat UI is unrelated;
both PRs edit the dashboard, so check conflicts when integrating. GPA simulation
and retake-attempt modeling remain outside this story.

[Student Handbook 2026-2027](https://drive.google.com/file/d/1nccONSadt3FNjqQUDhlxCxi5cHsy2UC5/preview).

| Grade | Points | Grade | Points |

| B+ | 3.33 | B | 3.00 |
| B- | 2.67 | C+ | 2.33 |

| D+ | 1.33 | D | 1.00 |
| F | 0.00 | FX | 0.00 |

The handbook excludes P, NP, I, IP and W from GPA. Notably FX is **0.00** in this
SDU source; another university's 0.50 scale must not be substituted. These values
were verified from the actual downloadable table, not inferred from percentages.
Sources checked on 22 October 2026. The full scale was absent from the repository;
the university's own published handbook fills that documented gap.

## Calculation and automatic behavior

`CumulativeGpaService` is the single calculation implementation:

`GPA = sum(grade points * course credits) / sum(eligible course credits)`.

It uses exact decimal arithmetic and rounds once at the end to two decimal
places. SDU's registrar specifies two decimals; HALF_UP retains the existing
dashboard formatter's convention for exact midpoint ties, which the university
FAQ does not separately specify. The rounded result drives the existing badge
thresholds as well as the displayed GPA.

Only the authenticated student's US-29 completion DTOs are supplied. Letter
codes are trimmed and case-normalized. Missing, non-GPA and unsupported codes,
and null/non-positive credits are excluded from both numerator and denominator.
F, FX and AW contribute zero points **and their positive credits remain in the
denominator**. Semester metadata is not required for a recorded grade to count.
Current enrollments and cart projections are never input to this calculation.

The dashboard loads the completion rows once and uses the same snapshot for
both history and GPA. Each subsequent page request recalculates after committed
grade additions, edits, removals or completion deletions, including updates from
outside this application. No manual calculation action, cached session GPA,
scheduled job, extra query, database trigger or live frontend polling is needed.
A page already open in a browser updates when reloaded/navigated to.

With zero eligible credits, GPA is null, displaying `N/A` and `Not Available`.
Partial histories calculate from eligible recorded grades; the card says
"Based on recorded grades". Unknown codes are safely omitted, never guessed or
treated as failures. Trusted transcript loading must use supported grade codes.

`Student.gpa` remains as a legacy column for compatibility, but the dashboard
does not read it or write aggregates during GET requests. `AcademicStandingDto`
now accepts an explicitly calculated GPA; no stored-value fallback remains.
No schema change or second migration is introduced. The existing JPQL read and
Java calculation work with both configured database engines without vendor SQL.

## Preserved behavior and limits

Completed/enrolled credit sums, degree progress and prerequisite membership use
the same pre-existing course sets. This story does not reinterpret completion
membership as passed/failed based on grades; that is separate from GPA eligibility.
Credits are current catalog credits, and there is one row per student/course.
Multiple attempts, grade equivalency and official transcript ingestion cannot be
reconstructed from the current schema and are not invented here.

Tests cover the full published scale, unequal weights, rounding, zero-point
grades, excluded/unknown/missing grades, invalid credits and overflow avoidance.
Database-backed dashboard tests cover repeated requests after grade changes,
new eligibility, removals, no eligible history, stale legacy GPA, two students in
the same course, request-parameter isolation, session guards and existing metrics.

The story is intentionally unestimated until the team supplies its estimate.
Project-board fields could not be assigned because the token lacks project scope.
Peer approval, the US-29 merge and retargeting to main are required before merge.
